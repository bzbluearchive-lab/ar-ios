# 走 kfd 的具体方案

## 一句话思路

**不手工往 SpringBoard 里塞代码，而是用 kfd 拆掉"平台二进制保护"这一道门，然后让我们现有的、已经跑通的注入代码自己去干活。**

理由：我们现在唯一被挡的地方是 `task_for_pid` 拿到的端口没有写权限（`vm_allocate -> 0x10000003`）。
只要把内核里那道检查关掉，`RemoteLoad.h` 一行都不用改，SpringBoard 注入就能通。
相比之下，"用 kfd 手工往目标进程的 vm_map 里塞页"要自己处理页表、pte、pmap，代码量大十倍，出错面也大十倍。

**所以 kfd 的用途被压缩成一件事：一次性的、范围极窄的内核补丁。**

## 设备侧现状（已确认的事实）

| 事实 | 来源 |
|---|---|
| iOS 16.1.1 / arm64e (M2 iPad) | 用户提供 |
| TrollStore 可用，可装无沙盒 app | 实测 |
| 无沙盒 app 能 `task_for_pid` 成功（252 个进程） | K5 实测 |

最后两条是关键证据：它用 kfd 突破平台保护，然后在 SpringBoard 层做浮窗。

## 分五步，每步都有验收和回滚

### 第 1 步：把 kfd 编进来，只跑初始化

- 源码：`felix-pb/kfd`（放在 `vendor/kfd/`，作为静态库编进 daemon）
- 16.1.1 arm64e 上可用的分支：`landa` 或 `physpuppet`（kfd 里按 iOS 版本表选）
- 这一版**只做**：`kfd_init` → 打印 `kfd_kbase()` → 退出

**验收**：日志里出现内核基址，且设备没重启。

**风险**：初始化阶段失败通常是直接 panic → 设备自动重启。这是可恢复的，重启后完全干净（我们什么盘都没写）。

**回滚**：删 app。

### 第 2 步：只读，不写

- 用 `kfd_kread` 读几个已知位置做自检：
  - 读当前进程的 `proc` 结构，校验 `p_pid` 等于 `getpid()`
  - 读 `proc->p_comm`，校验等于我们自己的二进制名
- 校验通过才继续；任一不符，立刻停止

**验收**：读回的数据和自己进程的实际信息一致。

**意义**：这一步证明"地址算对了"。地址错的时候**读**是安全的，写才致命——所以先只读。

### 第 3 步：定位那道门（只读分析）

目标是找到 `task_for_pid` 路径上拒绝"平台二进制"的那处检查。两条路：

1. **符号法**：kfd 支持读内核符号（`kallsyms` 风格），找到 `task_for_pid`、`proc_security_policy`、`cs_require_lv` 等相关符号地址
2. **特征扫描法**：在 `__TEXT_EXEC` 范围内扫指令特征（如果符号表不可用）

**验收**：找到候选函数地址，并把它反汇编出来人工核对（我需要你把那几十字节发我，我在本地用脚本反汇编确认）。

**注意**：这一步**仍然只读**。

### 第 4 步：一次最小补丁 + 立即回读校验

这是唯一写内核的一步，规则定死：

```
1. 先 kread 备份原始字节（N 条指令，通常 1~4 条）
2. kwrite 补丁
3. 立刻 kread 回读，逐字节比对预期
4. 比对失败 → 立刻写回原始字节
5. 无论成败，把"地址/原值/新值/校验结果"写进日志文件
6. app 里加一个「撤销补丁」按钮，把原始字节写回去
```

补丁形式优先选**最保守的那种**：

- 首选：把条件跳转改成无条件跳转 / NOP 掉几条检查指令
- 次选：把函数的返回值强制成 0
- 绝不做：改函数指针表、改结构体字段（影响面不可控）

**验收**：补丁后，我们现有的注入代码重跑，`vm_allocate` 从 `0x10000003` 变成 `0`。

**风险**：这是全程唯一可能 panic 的地方。写错 → 立即 panic → 自动重启。
理论上更坏的情况是写到了恰好映射到磁盘缓存的内核内存——概率极低，但这是"可能损坏数据"的唯一一类场景。所以：

- 只允许写 `__TEXT_EXEC`（代码段），**绝不写数据段**
- 写前必须通过第 2、3 步的地址校验
- 每次只改 1~4 条指令，不批量改

### 第 5 步：注入 SpringBoard

补丁生效后，直接复用现有代码：

```cpp
pid_t sb = rload::find_pid_comm("SpringBoard");
rload::inject_pid(sb, payloadPath);   // 和 G3 里那行一模一样
```

`vm_allocate` / `vm_write` / `thread_create` / `thread_resume` 全都能过了之后，
`SBWindow.mm` 那套选 scene + 建高层级窗口的代码就能跑起来。

**验收**：屏幕中央出现绿框，且能盖过通知中心。

## 代码结构

```
vendor/kfd/               kfd 源码（静态库）
src/Kernel/Kfd.h          init / kbase / kread / kwrite 的薄封装
src/Kernel/SelfCheck.h    第 2 步：读自己的 proc 做地址校验
src/Kernel/Patch.h        第 4 步：备份 → 打补丁 → 回读校验 → 撤销
src/Inject/RemoteLoad.h   不动（已验证的注入逻辑）
```

`Patch.h` 的形状（关键在"每一步都校验"）：

```cpp
struct PatchRecord {
    uint64_t addr;
    uint8_t  orig[16];
    uint8_t  patched[16];
    int      len;
    bool     applied;
};

// 返回值：0 成功，负数表示在哪一步失败
int apply_patch(PatchRecord& r);     // 备份 → 写 → 回读比对 → 失败自动写回
int revert_patch(PatchRecord& r);    // 把 orig 写回去，再回读校验
```

## 我做这件事的顺序（先做零风险的）

**在动 kfd 之前，先把「注入游戏进程」测掉。**

理由：那是零内核风险的，如果成立，你就已经有一个能用的 ESP 了——只是没有系统级浮窗。
kfd 唯一多给你的东西是"盖在所有窗口之上"，而它带来的是全程唯一的内核写风险。

所以顺序建议：

```
1. 注入游戏进程（零风险）        → 有了 ESP
2. FrontBoard scene 托管（低风险） → 如果能通，连 kfd 都不需要
3. kfd 拆平台保护（高风险的唯一一步） → 才有系统级浮窗
```

第 2 步值得先试：商业产品里同时出现了 `BackBoard` / `SBS`，说明它的浮窗确实在 SpringBoard 层；但它也可能有两条路（kfd 只是其中一条）。

---

## 我不能替你决定的

kfd 那一步的风险是**真实内核写**，不是"理论风险"：

- 写错地址 → 立即 panic，设备重启（可恢复）
- 极端情况下写到映射到磁盘缓存的内核内存 → 可能损坏数据（不可恢复，但概率极低）

我会把每一步做成可撤销、可回读校验、日志留痕，但它终究是往内核里写字。
你确认要上这一步，我就按上面五步走；不确认，我们就先把第 1、2 步（零风险那两条）走完。
