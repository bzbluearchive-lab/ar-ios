# 在 6s (15.8) 上做，能不能直接拿到主力机 (M2 / 16.1.1) 用

## 结论

**不能直接拷。** 但能省掉绝大部分工作。

区分三类东西：

| 类别 | 内容 | 能否移植 |
|---|---|---|
| **可复用（约 90%）** | app 骨架、daemon、进程查找、`RemoteLoad` 注入逻辑、`SBWindow` 浮窗、`Aim`/W2S、`Offsets.hpp` 的解析框架、整套诊断工具与打包流程 | ✅ 原样拿过去 |
| **不可复用** | kfd 的内核结构偏移、补丁地址与字节、exploit 分支选择 | ❌ 必须按各自设备重新算 |
| **需重新验证** | 整条注入链路在 16.1.1 / arm64e 上的实际行为 | ⚠️ 逻辑一样但结果要重测 |

## 为什么内核那部分不能拷

| 差异 | 后果 |
|---|---|
| **arm64 (A9) vs arm64e (M2)** | 指针认证、部分结构体布局（含 `proc_ro` 拆分后的字段顺序）不同 |
| **XNU 15 vs XNU 16** | `task_for_pid` 的检查代码不同 → 补丁位置、字节全都不同；15.x 与 16.x 的 `kalloc_type`、`proc_ro`/`task_ro` 布局也不同 |
| **kfd 的 exploit 分支** | 15.8 与 16.1.1 可用的漏洞不同（physpuppet / landa / smith 覆盖面不一样），初始化路径也不同 |

所以「在 6s 上算出来的一组内核偏移」拿到 M2 上**一个都用不了**。能带走的是**方法**：
「怎么用符号/特征找到那道检查、怎么安全地打补丁、怎么回读校验」这套流程，是设备无关的。

## 更关键的一点：6s 不需要 kfd

iPhone 6s 是 **A9（checkm8 漏洞）**，可以直接越狱（palera1n）。越狱后你拿到的是：

- root 权限
- 完整的注入框架（ellekit / 插件加载）
- 可以随便改 SpringBoard（tweak 直接进 SpringBoard，不需要任何内核 patch）
- 调试工具齐全（lldb、frida、Filza）

**这条路比 kfd 简单一个数量级，而且没有内核写的风险。** kfd 存在的意义只有一个：在**不能越狱**的设备上获得内核读写。6s 能越狱，就不需要它。

## 但 6s 有个硬限制

| 项 | 6s | 主力机 |
|---|---|---|
| CPU | A9（arm64，2 核） | M2（arm64e） |
| 内存 | 2 GB | 8/16 GB |
| 跑暗区 / 三角洲 | ❌ 跑不动（这类 UE4 手游要 4GB 内存起） | ✅ |

所以 6s 只能验证**机制**（注入、浮窗、W2S 数学、hook 时序），**没法验证"对着游戏出框"**。游戏相关的偏移必须在主力机上摸。

## 建议的分工

```
6s (越狱)  →  机制开发机
  · 验证浮窗能盖住游戏
  · 验证 W2S / 骨骼投影 / 自瞄数学
  · 验证 hook 与渲染时序
  · 用任意能跑起来的 3D 场景当靶子（不必是目标游戏）

主力机     →  目标验证机
  · 目标游戏 + 真实偏移
  · 最终注入与反作弊对抗
```

## 如果你坚持要在 6s 上走 kfd（而不是越狱）

那 6s 的价值就只剩「验证 kfd 能不能跑通」。要迁到 M2/16.1.1，必须重做的清单：

1. kfd 分支选择：按 16.1.1 / arm64e 选（不是 15.8 那个）
2. 内核基址获取方式是否一致
3. 重新定位 `task_for_pid` 的检查点（符号扫描或特征扫描）
4. 重新计算补丁字节，并在设备上回读校验
5. 重新验证整条注入链（`vm_allocate` 是否仍然返回 `0x10000003`）

**唯一能确定的是**：拿到 M2 上时，`vm_allocate` 会不会变成 0 —— 这必须实测，不能从 6s 的结果推断。

## 一句话总结

> 6s 上做出来的是「**方法和上层逻辑**」，可以整套搬到主力机；
> 「内核偏移和补丁字节」必须在主力机上重新算；
> 而 6s 既然能越狱，那连 kfd 都不必碰——直接越狱做机制验证更省事、更安全。
